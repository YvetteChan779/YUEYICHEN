Retrieval-Augmented Manipulation

Object-centric manipulation · a retrieval-first system design

A retrieval-first design for manipulating unseen objects: discover the object, retrieve a category template, reconstruct an object-centric 3D frame, then hand explicit geometry to a deterministic motion layer.

The Idea

Most manipulation policies try to learn the pixel-to-torque mapping end to end, which means every new object is a new data problem. The design bet here is the opposite: treat manipulation as retrieval first, motion second. If a robot can recognize what an object is and pull a matching 3D category template from memory, it inherits that category's grasp points, hinges, and support planes for free — so a single RGB frame of an unseen instance is enough to act on.

That bet forces one clean boundary: the hard contract is the object representation, not the robot SDK. The design splits into four decoupled stages — step1_grounding discovers object instances in a live RGB frame, step2_ram lifts them into an explicit object-centric 3D frame (viewpoint + NOCS + affordances), step3_planning turns that geometry into VLM subgoals, and step4_conducting converts subgoals into robot waypoints. Because geometry is explicit and every stage writes an inspectable artifact, the perception half can be debugged without ever touching the arm.

My role: I own the system design and the training-side pipeline on this page — the retrieval-first decomposition, the object-representation contract, and the RAMNet training scheme (frozen backbone, BOP-style data, template priors, the loss mix). The idea builds on published work by my senior colleague (Chen et al., Science Robotics 2026), reused here with permission; quantitative results are attributed to that paper rather than re-run locally.
What the design buys, per the paper: zero-shot real-world execution on unseen objects, spatially aware manipulation from a single 2D image, and adaptive replanning under physical constraints such as object size and collision.

Architecture

The design reuses strong off-the-shelf perception (GroundingDINO + SAM2 for discovery, VGGT-1B for metric depth) and spends its own learned capacity only where it matters — RAMNet, the module that fuses 2D features with a retrieved 3D template. Everything downstream of geometry stays deterministic on purpose.

RAMNet core — the learned bet

The one module worth training. visions/ram/lib/network.py keeps DINOv2-B/14 frozen (features from layers [7,9,11] concatenated to a 2304-D embedding) and learns only lightweight heads: a 1-layer view adapter, a 4-layer shape encoder, a 4-layer map adapter, and a 2304 → 512 → 256 → 3 deformation decoder. The design choice is to adapt a strong visual prior into geometry, not relearn vision.

Decoupled stages — why four scripts

Semantics, geometry, planning, and motion are deliberately separated: step1_grounding.py discovers objects, step2_ram.py estimates pose and functional priors, step3_planning.py decomposes the instruction into constraints, and step4_conducting.py emits waypoints. Each boundary is a file on disk, so a failure localizes to one stage instead of hiding inside an end-to-end net.

Training Scheme by Design

The training-side design follows from the idea: if the runtime retrieves category templates, then training should teach RAMNet to fit a template to observed pixels, not to memorize instances. So supervision comes from BOP-style scenes rendered with BlenderProc (--num-scenes 400, --views-per-scene 25), and each category is pre-rendered into 128 template views stored as obj_<id>.ply plus <template_id>.pkl — a reusable geometric memory the network can index at inference.

train_bop.py builds RAMNet from the DINOv2-B/14 checkpoint, freezes the foundation model (only non-foundation_model params are trainable), and optimizes a three-part objective that mirrors the three things the runtime needs: PoseNCE (view-contrastive, so retrieval picks the right viewpoint), NOCSLoss (dense object-coordinate regression, so geometry is metric), and MatchLoss (an entropy term that sharpens 2D-3D correspondence). Budget: 50 epochs, 2000 steps, batch size 4, lr 1e-4.

Templates are category-specific by design: template.json drives loading of grasp_*, contact_point_*, hinge*, and plane_* primitives, so what the runtime recovers is object-specific affordances (where to grasp, where it hinges, what surface supports it) rather than a generic bounding box.

Design consequence: this is structured geometry fitting, not end-to-end policy learning. Freezing the backbone keeps the visual prior intact while lightweight heads absorb category geometry — which is what makes single-image, zero-shot transfer to unseen instances plausible.

Runtime and Control

Once geometry is explicit, motion should be boring and predictable — that is the design intent. PathPlanner runs a 100³ voxel costmap (max_steps=300, stop_threshold=0.001, target_map_weight=2, obstacle_map_weight=1, pushing_skip_per_k=5). TrajectoryGenerator converts voxels to base-frame poses, clamps Z to table_height, and emits waypoints carrying orientation and gripper state.

controller/fairino_arm.py wraps the Fairino Robot.RPC interface, issuing MoveL at velocity 60, MoveC at velocity 20, plus gripper commands. Keeping this a conventional, inspectable motion layer — rather than a learned policy — means the intelligence lives in the object representation, and execution stays auditable and safe to clamp.

The four-script split pays off at debug time: camera calibration, VGGT depth rescaling, template lookup, and constraint parsing each fail in their own file, with their own artifact, so root-causing a bad grasp does not require unwinding the whole stack.

What the Design Achieves

Attributed to the paper (Chen et al., Science Robotics 2026) and the CUHK release: the system was evaluated across 14 manipulation tasks spanning 31 objects, demonstrating zero-shot real-world execution, spatially aware manipulation from a single 2D image, and adaptive replanning under physical constraints such as object size and collision. The release also reports CO3D generalization to unseen categories and robustness to shape and occlusion variation.

I present these as the paper's reported outcomes, not as numbers I re-measured. Per-task success rates and baseline deltas are not disclosed in the publicly accessible article or repository, so I deliberately do not quote a headline percentage here — the contribution I claim is the system design and the training-side scheme, which I verified line-by-line against the code.

Honest scope: a full run needs external assets that are not vendored — Grounded-SAM-2, VGGT, DINOv2-B/14, the Fairino SDK, and the RAM template payloads. The repo exposes the complete code path but no benchmark logbook, so any quantitative claim on this page traces to the publication, not to a local rollout.
